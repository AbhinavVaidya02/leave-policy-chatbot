## 1. Project Overview

A Retrieval-Augmented Generation (RAG) chatbot that answers employee questions about Flairminds Software's leave policy. The chatbot reads a single PDF source document, indexes it offline, and at query time retrieves the most relevant sections before generating a grounded answer using a large language model.

**Design goals:**
- Answers are strictly grounded in the policy document — the LLM is instructed to say "not in the context" rather than hallucinate.
- No re-embedding on every app start — the index is built once and loaded from disk.
- Minimal footprint — no external vector database, no orchestration framework.

## 4. Module Breakdown

### `ingest.py` — Offline Indexer

A one-shot CLI script. Responsible for the full ingestion pipeline: load PDF → chunk → embed → build index → save to disk. Must be re-run whenever the source PDF changes. Does not start a server or serve any requests.

Key calls in order:
```
RAGEngine.load_pdf()  →  chunk_text()  →  build_index()  →  save_index()
```

### `main.py` — Streamlit UI

Handles all user-facing concerns. Uses Streamlit's `session_state` to:
- Cache the `RAGEngine` instance across reruns (avoids re-loading the index on every interaction).
- Maintain the full chat message history for display.

On each user message, it calls `engine.chat(query, chat_history)` and appends both the user message and the assistant reply to session state. The sidebar provides a "Clear chat" button and source document info.

### `rag_engine.py` — RAGEngine Class

The single class that owns all RAG logic. Breaking it into logical sections:

| Method | Responsibility |
|---|---|
| `__init__` | Configures Google Generative AI, initialises empty index/chunk/BM25 slots |
| `load_pdf` | Extracts raw text from each PDF page via `pypdf` |
| `chunk_text` | Splits text into overlapping fixed-size chunks |
| `_embed` | Calls Google Embedding API with the correct task type |
| `embed_document` | Wraps `_embed` with `task_type="retrieval_document"` |
| `embed_query` | Wraps `_embed` with `task_type="retrieval_query"` |
| `build_index` | Builds both FAISS and BM25 indexes from chunks |
| `save_index` | Persists FAISS index + chunks list + BM25 index to disk |
| `load_index` | Restores all three from disk; returns `False` if index files are missing |
| `is_ready` | Guard check — returns `True` only if index and chunks are loaded |
| `retrieve` | Pure dense vector search (kept for fallback/testing) |
| `retrieve_hybrid` | Hybrid search: dense + BM25 fused with RRF (primary retrieval path) |
| `generate_answer` | Builds a grounded prompt and calls the Gemini LLM |
| `chat` | Main entry point: `retrieve_hybrid` → `generate_answer` |

## 5. Data Flow

### Ingestion (Offline)

```
Leave Policy.pdf
    │
    ▼  load_pdf()
Raw text string (~6,849 characters)
    │
    ▼  chunk_text(size=1000, overlap=200)
List of 9 text chunks
    │
    ├──► embed_document() × 9  ──►  Google Embedding API
    │         └──► 9 float32 vectors (shape: 9 × embedding_dim)
    │              └──► faiss.normalize_L2()
    │              └──► FAISS IndexFlatIP  ──►  index.faiss
    │
    ├──► BM25Okapi(tokenized_chunks)  ──►  bm25.pkl
    │
    └──► chunks list  ──►  chunks.pkl
```

### Query (Runtime)

```
User question: "When does comp off expire?"
    │
    ├──► [Dense leg]
    │    embed_query()  →  Google Embedding API  →  query vector
    │    faiss.normalize_L2(query_vector)
    │    FAISS.search(query_vector, fetch_k=15)  →  dense ranked list
    │
    ├──► [Sparse leg]
    │    query.lower().split()  →  tokens
    │    BM25.get_scores(tokens)  →  score per chunk
    │    np.argsort(scores)[::-1]  →  sparse ranked list
    │
    ├──► [RRF Fusion]
    │    For each chunk in (dense ∪ sparse):
    │        score = 1/(60 + dense_rank) + 1/(60 + sparse_rank)
    │    Sort by fused score → top 5 chunks
    │
    └──► generate_answer(question, top_5_chunks, last_6_chat_turns)
              │
              ▼  Gemini 2.5 Flash
         Final answer string  →  Streamlit UI
```

## 6. Chunking Strategy

**Method:** Fixed-size character-level sliding window with overlap.

| Parameter | Value |
|---|---|
| `CHUNK_SIZE` | 1,000 characters |
| `CHUNK_OVERLAP` | 200 characters |
| Result on this doc | 9 chunks |

**Why overlap?** Policy sentences near chunk boundaries would otherwise be split across two chunks, causing neither chunk to carry the full context of the clause. A 200-character overlap ensures boundary content appears in both adjacent chunks.

**Trade-off:** Overlap means some text is duplicated in the index. This is acceptable at small scale but increases embedding cost and index size proportionally to the overlap ratio (20% here).

**Current limitation:** Chunking is purely character-based. It is not aware of paragraph, section, or sentence boundaries, which can produce mid-sentence chunk starts (e.g., Chunk 1 begins with `"nly this type..."` because `"O"` was at position 800 of the previous chunk).

## 7. Embedding Model

**Model:** `models/gemini-embedding-2` (Google Gemini Embedding v2)

**Task-type asymmetry:** The Gemini embedding API accepts a `task_type` parameter that optimises the embedding for different roles. This chatbot uses two distinct types:

| Call site | `task_type` | Purpose |
|---|---|---|
| `embed_document()` | `retrieval_document` | Optimised for indexing passages |
| `embed_query()` | `retrieval_query` | Optimised for matching a user question to passages |

This asymmetry (document vs. query embeddings) is a standard technique — the embedding space for a passage and the query seeking that passage are intentionally different. Using the wrong task type at either end degrades retrieval quality.

**Normalisation:** After embedding, `faiss.normalize_L2()` is applied to both document vectors (at build time) and query vectors (at retrieval time). This converts the inner-product similarity computed by `IndexFlatIP` into cosine similarity.

## 8. Search Mechanism — Hybrid Search

The chatbot uses **hybrid search**: a combination of dense vector search and sparse keyword search, fused using Reciprocal Rank Fusion (RRF).

### Dense Search (Semantic)

- **Index type:** `faiss.IndexFlatIP` — exact inner product (cosine after L2 normalisation)
- **Finds:** Chunks semantically similar to the query, even when exact words differ
- **Good for:** Conceptual questions, paraphrases, synonym matching
- **Weak at:** Exact proper nouns, system names, specific numeric values

### Sparse Search (Keyword — BM25)

- **Library:** `rank_bm25.BM25Okapi`
- **Tokenisation:** Lowercased whitespace split
- **Finds:** Chunks containing the exact query terms, ranked by term frequency and inverse document frequency
- **Good for:** Proper nouns (`Zymmer`), HRMS leave-type names (`Working late today`, `Visiting client location`), specific numbers (`8 days`, `3 months`)
- **Weak at:** Paraphrases, synonyms

### Reciprocal Rank Fusion (RRF)

Both legs independently rank all chunks. RRF combines the two ranked lists:

```
rrf_score(chunk) = 1 / (k + dense_rank) + 1 / (k + sparse_rank)
```

Where `k = 60` (standard constant that dampens the influence of very high ranks). Chunks that appear highly ranked in **both** lists receive the highest fused scores. Chunks that appear in only one list are still included but score lower.

| Setting | Value |
|---|---|
| RRF constant `k` | 60 |
| Candidates per leg (`fetch_k`) | `TOP_K × 3 = 15` |
| Final results returned | `TOP_K = 5` |

**Fallback:** If `bm25.pkl` is absent (e.g., old index built before the hybrid update), `retrieve_hybrid()` automatically falls back to `retrieve()` (dense-only).

### Why Not Just Dense or Just BM25?

| Query type | Dense alone | BM25 alone | Hybrid |
|---|---|---|---|
| "time off for sick child" | Good | Misses | Good |
| "Zymmer logging hours" | Poor | Good | Good |
| "how many casual days" | Good | Good | Good |
| "Working late today entry" | Unreliable | Good | Good |

## 9. LLM & Answer Generation

**Model:** `models/gemini-2.5-flash` (Google Gemini 2.5 Flash)

**Prompt structure:**

```
[System role] You are a helpful HR assistant for Flairminds Software.
              Answer strictly from the leave policy context provided.
              If not in context, say so clearly.

[Context block] Leave Policy Context:
                <chunk_1>
                ---
                <chunk_2>
                ...

[History block] Previous conversation:
                User: ...
                Assistant: ...   (last 6 turns)

[Current turn]  User: <question>
                Assistant:
```

**Grounding constraint:** The system instruction explicitly restricts the model to the provided context. This prevents hallucination of policy terms that are not in the source document.

**Context window usage:** Top-5 chunks of ~1,000 characters each = ~5,000 characters of policy context per request. Well within Gemini 2.5 Flash's context window.

## 10. Chat History Management

Chat history is maintained at two layers:

| Layer | Where | Purpose |
|---|---|---|
| Display history | `st.session_state["messages"]` | Full conversation shown in the UI |
| LLM context window | Last 6 messages passed to `generate_answer` | Keeps the prompt size bounded |

The `generate_answer` method slices `chat_history[-6:]` before building the prompt. This means only the 3 most recent question-answer pairs inform the LLM's response. Older turns affect the display but not the generation.

**Why 6?** A balance between conversational coherence (enough context to resolve follow-up pronouns like "it" or "that policy") and prompt token efficiency.

## 11. Index Persistence

Running `ingest.py` produces three files in `faiss_index/`:

| File | Content | Library |
|---|---|---|
| `index.faiss` | FAISS dense vector index | `faiss.write_index` / `faiss.read_index` |
| `chunks.pkl` | Raw text chunks (list of strings) | `pickle` |
| `bm25.pkl` | BM25Okapi object | `pickle` |

On app start, `load_index()` reads all three. The `RAGEngine` instance is then cached in `st.session_state["rag_engine"]` so the disk read happens only once per Streamlit session, not on every UI rerender.

**When to re-run `ingest.py`:**
- The source PDF (`Leave Policy.pdf`) is updated
- Chunking parameters (`CHUNK_SIZE`, `CHUNK_OVERLAP`) are changed
- The embedding model is changed (embeddings become incompatible)

## 12. Configuration & Environment

All configuration lives in two places:

**`.env` file (secrets):**
```
GOOGLE_API_KEY=<your-google-ai-studio-key>
```

**Constants in `rag_engine.py` (tuneable parameters):**

| Constant | Default | Effect |
|---|---|---|
| `GOOGLE_EMBEDDING_MODEL` | `models/gemini-embedding-2` | Embedding model used for both indexing and querying |
| `GOOGLE_LLM_MODEL` | `models/gemini-2.5-flash` | LLM used for answer generation |
| `CHUNK_SIZE` | `1000` | Characters per chunk — larger = more context per chunk, fewer chunks |
| `CHUNK_OVERLAP` | `200` | Overlap between consecutive chunks — reduces boundary split issues |
| `TOP_K` | `5` | Number of chunks retrieved and passed to the LLM |
| `INDEX_DIR` | `"faiss_index"` | Directory where the index files are saved/loaded |

Changing `CHUNK_SIZE`, `CHUNK_OVERLAP`, or `GOOGLE_EMBEDDING_MODEL` requires a full re-index (`python ingest.py`).

## 14. Setup & Running

### First-time setup

```bash
# 1. Create and activate virtual environment
python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # macOS/Linux

# 2. Install dependencies
pip install -r requirements.txt

# 3. Set API key
cp .env.example .env
# Edit .env and add your GOOGLE_API_KEY

# 4. Build the index (one-time)
python ingest.py
```

### Running the app

```bash
streamlit run main.py
```

### Rebuilding the index (after PDF update)

```bash
python ingest.py
```
Then refresh the Streamlit app (it will reload the index from disk on next startup).

## 15. Known Limitations

| Limitation | Detail |
|---|---|
| Single document source | The system is designed for one PDF. Adding multiple documents requires changes to `ingest.py` and the chunk/index management logic. |
| Character-level chunking | Chunks may start or end mid-sentence. A sentence-aware or paragraph-aware splitter (e.g., spaCy) would improve chunk quality. |
| No chunk metadata | Chunks carry no page number, section title, or source reference. Retrieval results cannot cite a specific policy clause number or page. |
| BM25 tokenisation is naive | Whitespace splitting does not handle punctuation, stemming, or stop words. A tokeniser like NLTK would improve sparse retrieval quality. |
| Chat history is not persisted | Clearing or restarting the browser tab loses the conversation. There is no database-backed history store. |
| No reranking step | After RRF fusion, chunks are passed directly to the LLM with no cross-encoder reranking. Adding a reranker (e.g., Cohere Rerank) would further improve context quality. |
| No streaming | The LLM response is generated fully before being displayed. Streaming via `generate_content(..., stream=True)` would improve perceived response latency. |
| Deprecated SDK | `google-generativeai` is the old client. Should migrate to `google-genai` at the next opportunity. |
